# 프로젝트 요구사항

## 1. 프로젝트 개요

- 한글 이름: 플레이어 지원 데스크
- 영문 이름: Player Support Desk
- 저장소명: `player-support-desk`
- 성격: 가상의 글로벌 게임 서비스 고객 문의(VOC) 운영 대시보드
- 주요 사용자: 접수된 고객 문의를 조회하고 처리하는 운영 담당자

실제 회사나 게임의 로고와 저작물을 사용하지 않고, 가상의 서비스와 데이터만 사용합니다.

## 2. 목적

이 프로젝트는 다음 두 가지 목적을 갖습니다.

1. 운영자가 문의 현황과 우선순위를 빠르게 파악하고, 상태·담당자·메모를 관리할 수 있는 반응형 도구를 구현합니다.
2. React 프로젝트 경험을 바탕으로 Vue 3, Composition API, TypeScript를 학습하고 결과물로 완성한 실행력을 사실 기반으로 보여줍니다.

증명하려는 역량은 다음과 같습니다.

- 컴포넌트 기반 UI 설계와 Props/Emit 활용
- TypeScript 데이터 모델링
- REST API 연동과 비동기 상태 처리
- Pinia를 이용한 공유 상태 관리
- 데스크톱·태블릿·모바일 반응형 구현
- 로딩·오류·빈 상태 등 실제 서비스 상태 처리
- 접근성, 기본 성능 최적화, 자동화 테스트
- 브랜치, 커밋, Pull Request를 활용한 개발 과정

## 3. 범위 밖의 작업

- 실제 인증과 권한 관리
- 실제 데이터베이스와 운영 백엔드
- 실시간 채팅과 WebSocket
- 파일 첨부와 이미지 업로드
- 실제 회사·게임 데이터 또는 브랜드 자산 사용
- 상위 폴더에 있는 기존 이력서 수정

## 4. 핵심 사용자 흐름

1. 운영자가 대시보드에서 전체, 신규, 처리 중, SLA 지연 문의 수를 확인합니다.
2. 문의 목록에서 검색, 상태, 우선순위, 카테고리 필터와 정렬을 사용합니다.
3. 문의를 선택해 본문, 고객 정보, 접수 정보, 처리 이력을 확인합니다.
4. 문의 상태와 담당자를 변경합니다.
5. 운영 메모를 작성합니다.
6. 변경 결과가 상세, 목록, 대시보드 통계에 반영됩니다.

## 5. 화면 요구사항

### 대시보드 `/`

- 전체 문의 수
- 신규 문의 수
- 처리 중 문의 수
- SLA 지연 문의 수
- 최근 접수 문의
- 우선순위별 문의 분포
- 최초 로딩과 API 오류 재시도

### 문의 목록 `/inquiries`

- 문의 번호, 제목, 카테고리, 고객 닉네임
- 국가 또는 언어, 우선순위, 상태, 접수 시각, 담당자
- 검색
- 상태·우선순위·카테고리 필터
- 최신순·오래된순 정렬
- 페이지네이션 또는 더 보기
- 필터 초기화
- 목록 로딩, 검색 결과 없음, 필터 결과 없음, API 오류와 재시도
- URL Query Parameter와 필터 상태 동기화

### 문의 상세 `/inquiries/:id`

- 문의 제목과 본문
- 고객 정보와 접수 정보
- 상태 변경
- 담당자 변경
- 처리 이력
- 운영 메모 작성
- 목록으로 돌아가기
- 존재하지 않는 문의
- 저장 중, 성공, 실패 상태
- 빈 메모 제출 검증

## 6. 도메인 모델

### 문의 상태

- `NEW`: 신규
- `IN_PROGRESS`: 처리 중
- `WAITING_CUSTOMER`: 고객 답변 대기
- `RESOLVED`: 해결

### 우선순위

- `URGENT`: 긴급
- `HIGH`: 높음
- `NORMAL`: 보통
- `LOW`: 낮음

### 카테고리

- 계정
- 결제
- 게임 오류
- 신고
- 설치 및 실행
- 기타

### 주요 TypeScript 타입

- `Inquiry`
- `InquiryStatus`
- `InquiryPriority`
- `InquiryCategory`
- `Customer`
- `Agent`

- `InquiryNote`

- `ApiError`

## 7. REST API

| Method | Endpoint | 역할 |
| --- | --- | --- |
| `GET` | `/api/dashboard` | 대시보드 통계 조회 |
| `GET` | `/api/agents` | 배정 가능한 담당자 목록 조회 |
| `GET` | `/api/inquiries` | 문의 검색·필터·정렬·페이지 조회 |
| `GET` | `/api/inquiries/:id` | 문의 상세 조회 |
| `PATCH` | `/api/inquiries/:id` | 상태 또는 담당자 변경 |
| `POST` | `/api/inquiries/:id/notes` | 운영 메모 추가 |

목록 API는 다음 Query Parameter를 처리합니다.

- `search`
- `status`
- `priority`
- `category`
- `sort`
- `page`
- `limit`

API는 MSW로 구현하지만 애플리케이션에서는 실제 REST API와 동일하게 `fetch`로 호출합니다. 변경된 가상 데이터는 `localStorage`에 저장해 새로고침 후에도 유지합니다.

- 목록은 `{ data, pagination }`, 담당자는 `{ data }` 형태로 반환합니다.
- 실패 응답은 `{ error: { code, message, details? } }` 형태로 통일합니다.
- 목록의 기본값은 최신순, 1페이지, 페이지당 10건이며 `limit`은 최대 50입니다.
- 메모는 공백 제거 후 1자 이상 1,000자 이하만 허용합니다.

## 8. 상태 관리

- Pinia: 문의 목록, 상세 데이터, 조회 상태, 변경 결과 등 화면 간 공유 상태
- URL Query Parameter: 목록 검색, 필터, 정렬, 페이지
- 컴포넌트 로컬 상태: 메모 입력, 필터 패널 펼침 여부 등
- MSW와 `localStorage`: 가상 API 데이터의 원본과 영속화

## 9. 반응형 요구사항

- `1200px` 이상: 사이드바와 테이블 중심의 데스크톱 레이아웃
- `768px~1199px`: 축약된 사이드바 또는 상단 내비게이션
- `767px` 이하: 테이블 대신 문의 카드 목록
- 모바일 필터는 접을 수 있는 패널로 제공
- 모바일 상세 화면의 변경 컨트롤은 충분한 터치 영역 확보
- 가로 스크롤에 의존하지 않음
- CSS 미디어 쿼리를 직접 작성하고 Flex와 Grid를 목적에 맞게 사용

## 10. 접근성과 성능

### 접근성

- 시맨틱 HTML과 명확한 heading 구조
- 버튼과 폼 컨트롤의 label
- 텍스트를 포함한 상태·우선순위 표시
- 키보드 조작과 명확한 포커스 스타일
- 저장 성공·실패 안내를 위한 `aria-live`
- 충분한 색상 대비
- `prefers-reduced-motion` 고려

### 성능

- 상세 페이지 라우트 Lazy Loading
- 검색 입력 Debounce
- 파생 값은 `computed`로 관리
- 안정적인 목록 key 사용
- 요청 경합 방지와 필요 시 AbortController 적용

## 11. 테스트 최소 기준

1. 상태 필터 선택 시 해당 문의만 표시됩니다.
2. 검색어 입력 시 목록이 변경됩니다.
3. 상태 변경 성공 시 화면과 Store가 갱신됩니다.
4. API 실패 시 오류 UI와 다시 시도 버튼이 표시됩니다.
5. 빈 운영 메모 제출이 차단됩니다.
