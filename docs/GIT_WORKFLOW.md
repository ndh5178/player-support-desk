# Git 브랜치 및 협업 전략

브랜치와 커밋의 크기는 `WORK_UNITS.md`의 작업 단위와 완료 기준을 따릅니다.

## 1. 선택한 전략

이 저장소는 `develop` 브랜치가 없는 가벼운 GitHub Flow를 사용합니다.

```text
main
  └─ 작업 브랜치 생성
       └─ 기능별 커밋
            └─ Pull Request
                 └─ 검증 후 main 병합
                      └─ 작업 브랜치 삭제
```

이 프로젝트는 한 명이 짧은 기간에 개발하고, 여러 기능을 별도 스테이징 환경에서 장기간 통합할 필요가 없습니다. 따라서 `main → develop → feature` 구조보다 항상 배포 가능한 `main`과 짧은 작업 브랜치가 목적에 맞습니다.

## 2. 브랜치 원칙

- `main`은 항상 타입 검사, 린트, 테스트, 빌드가 통과하는 상태로 유지합니다.
- 기능과 설정 변경은 최신 `main`에서 작업 브랜치를 만들어 시작합니다.
- 한 브랜치는 하나의 명확한 목적만 가집니다.
- 작업 브랜치는 가능한 짧게 유지합니다.
- 완료된 브랜치는 Pull Request로 병합한 뒤 삭제합니다.
- 관련 없는 사용자 변경을 같은 브랜치에 포함하지 않습니다.
- 긴급한 이유가 없는 한 `main`에 직접 커밋하지 않습니다.

## 3. 브랜치 이름

형식은 `<종류>/<짧은-kebab-case-설명>`입니다.

| 종류 | 용도 | 예시 |
| --- | --- | --- |
| `feature/` | 사용자 기능 | `feature/inquiry-list` |
| `fix/` | 버그 수정 | `fix/mobile-filter-layout` |
| `test/` | 테스트 중심 변경 | `test/core-flows` |
| `docs/` | 문서 변경 | `docs/project-foundation` |
| `chore/` | 설정과 도구 | `chore/project-setup` |

예정된 주요 브랜치는 다음과 같습니다.

```text
docs/project-foundation
chore/project-setup
feature/mock-api
feature/dashboard
feature/inquiry-list
feature/inquiry-detail
feature/responsive-ui
test/core-flows
docs/readme
```

실제 변경 범위가 달라지면 이름을 억지로 유지하지 않고 목적에 맞게 조정합니다.

## 4. 커밋 메시지

Conventional Commits의 타입을 사용하고 제목은 이해하기 쉬운 한국어로 작성합니다. 모든 커밋에는 제목뿐 아니라 변경 이유와 핵심 내용을 설명하는 본문도 함께 작성합니다.

```text
<type>: <변경 목적>

<이 변경이 필요한 이유>
<구현하거나 수정한 핵심 내용>
```

| 타입 | 용도 |
| --- | --- |
| `feat` | 사용자에게 보이는 기능 |
| `fix` | 오류 수정 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 |
| `style` | 동작과 무관한 코드 형식 |
| `refactor` | 동작을 유지한 구조 개선 |
| `perf` | 성능 개선 |
| `chore` | 설정, 의존성, 도구 |

좋은 예:

```text
feat: 문의 상태와 우선순위 필터 구현

운영자가 많은 문의에서 필요한 항목을 빠르게 찾을 수 있도록
상태와 우선순위 조건을 URL Query Parameter와 동기화했습니다.

필터 변경 시 페이지를 초기화하고 이전 목록 요청을 취소해
늦게 도착한 응답이 최신 결과를 덮어쓰지 않도록 처리했습니다.
```

피할 예:

```text
update
수정
작업 중
final
버그 수정
```

### 제목 작성 기준

- 명령형으로 무엇을 변경했는지 한 문장으로 표현합니다.
- 파일명보다 사용자 기능이나 변경 목적을 중심으로 작성합니다.
- 마침표를 붙이지 않습니다.
- 제목만 읽어도 커밋의 범위를 파악할 수 있게 작성합니다.

### 본문 작성 기준

- 제목 다음에 빈 줄을 둡니다.
- 코드가 무엇인지 반복하기보다 변경이 필요한 이유를 먼저 설명합니다.
- 구현한 핵심 동작, 중요한 제약, 이전 동작과의 차이를 기록합니다.
- 관련 검증이나 후속 작업이 중요하면 마지막 문단에 덧붙입니다.
- 사소한 표현을 과장하거나 실제로 수행하지 않은 검증을 작성하지 않습니다.

### 커밋 단위

- 하나의 커밋에는 하나의 설명 가능한 목적만 담습니다.
- 기능과 무관한 대규모 정리를 같은 커밋에 섞지 않습니다.
- 커밋 시점에 해당 범위가 실행 가능하고 관련 검증이 통과해야 합니다.
- 의미 없는 커밋 수를 늘리거나 날짜를 인위적으로 분산하지 않습니다.
- 이미 공개된 커밋은 특별한 이유 없이 다시 쓰지 않습니다.

## 5. 작업 절차

### 새 작업 시작

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/inquiry-list
```

원격 변경을 가져오는 명령은 연결 상태와 사용자 승인을 확인한 뒤 실행합니다.

### 변경 확인과 커밋

```bash
git status --short
git diff
git add <관련 파일>
git diff --cached
git commit
```

`git add .`에 의존하지 않고 커밋 목적과 관련된 파일을 확인해 스테이징합니다.

명령행에서 바로 작성할 때는 제목과 본문을 분리합니다.

```bash
git commit \
  -m "feat: 문의 목록 검색과 필터 구현" \
  -m "운영자가 필요한 문의를 빠르게 찾을 수 있도록 검색과 필터를 추가했습니다. 필터 상태를 URL Query Parameter와 동기화해 새로고침과 링크 공유를 지원합니다."
```

### Pull Request 전

```bash
npm run type-check
npm run lint
npm run test:unit
npm run build
```

최신 `main`과 차이가 크다면 rebase하고 다시 검증합니다.

```bash
git fetch origin
git rebase origin/main
```

## 6. Pull Request

- 제목은 대표 커밋과 같은 형식으로 작성합니다.
- 본문은 `.github/pull_request_template.md`를 사용합니다.
- 구현 목적, 변경 내용, 확인 방법, 검증 결과를 작성합니다.
- UI 변경은 가능한 경우 데스크톱과 모바일 화면 자료를 첨부합니다.
- 학습한 Vue 개념이 있다면 실제 파일과 함께 기록합니다.
- 검증되지 않은 항목은 체크하지 않습니다.

혼자 개발하더라도 PR을 사용하는 이유는 다음과 같습니다.

- 변경 범위를 병합 전에 다시 확인할 수 있습니다.
- 기능 단위의 설명과 검증 기록이 남습니다.
- 브랜치와 충돌 해결 과정을 실제로 연습할 수 있습니다.
- 저장소를 보는 사람이 개발 과정을 따라갈 수 있습니다.

## 7. 병합 방식

기본 병합 방식은 **Rebase and merge**입니다.

- 의미 있게 나눈 개별 커밋을 유지합니다.
- `main` 이력을 직선으로 읽을 수 있습니다.
- 기능이 추가된 순서를 파악하기 쉽습니다.

다음 경우에는 **Squash and merge**를 사용할 수 있습니다.

- PR에 의미 없는 WIP 커밋이 포함된 경우
- 여러 수정 커밋이 하나의 목적을 반복하는 경우
- 개별 커밋을 유지하는 가치보다 하나의 완결된 변경으로 남기는 가치가 큰 경우

병합 전에는 자동화 검증과 PR 체크리스트를 다시 확인합니다.

## 8. Merge Conflict 처리

충돌은 어느 한쪽 코드를 무조건 선택하는 문제가 아니라 양쪽 변경 의도를 이해하고 통합하는 작업입니다.

1. 현재 작업 내용을 커밋하거나 안전하게 보관합니다.
2. 최신 `main`을 가져옵니다.
3. 작업 브랜치에서 `main`을 rebase합니다.
4. 충돌 파일의 양쪽 변경 의도를 확인합니다.
5. 충돌 표시를 제거하고 요구사항에 맞게 통합합니다.
6. 해결한 파일을 스테이징하고 rebase를 계속합니다.
7. 관련 테스트와 전체 검증을 다시 실행합니다.
8. PR에 충돌 원인과 해결 방식을 간단히 기록합니다.

```bash
git fetch origin
git rebase origin/main
# 충돌 파일 수정
git add <해결한 파일>
git rebase --continue
```

해결 방향이 불명확하면 `rebase --abort`로 안전하게 이전 상태로 돌아간 뒤 확인합니다.

```bash
git rebase --abort
```

연습을 위해 만든 충돌은 실제 기능 개발 이력처럼 과장하지 않고 별도 실습 브랜치에서 진행합니다.

## 9. 보호와 금지 사항

- 비밀키, 토큰, 개인정보를 커밋하지 않습니다.
- `.env` 파일은 필요한 예시만 `.env.example`로 제공합니다.
- `git reset --hard`, 강제 푸시, 공개 이력 재작성은 명확한 이유와 확인 없이 사용하지 않습니다.
- 다른 사람이 만든 변경을 임의로 되돌리지 않습니다.
- 프로젝트 외부 파일을 스테이징하지 않습니다.
- 문제가 있는 검증을 삭제하거나 우회해서 병합하지 않습니다.
