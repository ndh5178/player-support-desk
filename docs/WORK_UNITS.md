# 작업 단위와 완료 기준

이 문서는 프로젝트를 어떤 크기로 나누어 구현하고, 각 작업을 언제 완료로 판단할지 정의합니다. 세부 요구사항은 `PROJECT_SPEC.md`, 순서와 진행 상태는 `IMPLEMENTATION_PLAN.md`, Git 절차는 `GIT_WORKFLOW.md`를 기준으로 합니다.

## 1. 작업 단위의 계층

작업은 파일 수가 아니라 사용자가 확인할 수 있는 기능과 변경 목적을 기준으로 나눕니다.

```text
프로젝트
└─ Pull Request: 하나의 완결된 기능 또는 기반 작업
   └─ 커밋: 기능을 구성하는 하나의 기술적 목적
      └─ 파일: 해당 목적에 필요한 코드, 스타일, 테스트, 문서
```

### Pull Request

- 사용자가 확인할 수 있는 하나의 기능이나 독립적인 기반 작업을 담습니다.
- 다른 PR 없이도 변경 목적과 검증 방법을 설명할 수 있어야 합니다.
- 타입 검사, 린트, 관련 테스트, 빌드를 통과한 상태로 병합합니다.
- UI 변경이면 해당 범위의 반응형과 접근성을 함께 확인합니다.

### 커밋

- PR을 구성하는 하나의 기술적 목적을 담습니다.
- 제목과 본문으로 변경 내용뿐 아니라 변경 이유를 설명합니다.
- 가능한 한 실행 가능하고 관련 검증이 통과하는 상태로 남깁니다.
- 기능, 무관한 정리, 문서 변경을 이유 없이 한 커밋에 섞지 않습니다.

### 파일

- 커밋 목적을 달성하는 데 필요한 파일만 포함합니다.
- 파일 종류가 다르다는 이유만으로 구현과 관련 테스트를 불필요하게 분리하지 않습니다.
- 프로젝트 외부 파일과 관련 없는 사용자 변경은 포함하지 않습니다.

## 2. 작업 분리 기준

다음 질문 중 하나라도 별도로 답해야 한다면 작업 단위를 분리합니다.

- 사용자가 독립적으로 확인할 수 있는 다른 기능인가?
- 실패하거나 되돌릴 때 다른 기능과 분리할 필요가 있는가?
- 다른 검증 방법이나 완료 조건이 필요한가?
- 변경 이유가 하나의 PR 제목과 설명으로 자연스럽게 표현되지 않는가?
- 리뷰할 때 서로 다른 기술적 판단이 필요한가?

반대로 하나의 기능을 완성하는 Template, Store, API, 스타일, 테스트는 파일 위치가 다르더라도 같은 PR 안에서 함께 다룰 수 있습니다.

## 3. 전체 작업 단위

### 0. 프로젝트 기준 문서

- 브랜치: `docs/project-foundation`
- 결과: 요구사항, 작업 규칙, 기술 결정, 학습 기준, QA, Git 전략
- 검증: 문서 링크, 파일 존재 여부, `git diff --check`

### 1. 개발 환경 구성

- 브랜치: `chore/project-setup`
- 결과: 실행 가능한 Vue 3 프로젝트와 개발 도구
- 포함:
  - Vue 3, TypeScript, Vite
  - Vue Router, Pinia
  - ESLint, Prettier
  - Vitest, Vue Test Utils
  - MSW 초기 설정
  - 기본 AppShell과 디자인 토큰
- 검증: 개발 서버, 타입 검사, 린트, 기본 테스트, 프로덕션 빌드

### 2. 도메인 모델과 Mock API

- 브랜치: `feature/mock-api`
- 결과: 화면에서 실제 REST API처럼 사용할 수 있는 가상 API
- 포함:
  - TypeScript 도메인 모델
  - 가상 문의 데이터
  - 검색·필터·정렬·페이지네이션
  - 상세 조회, 변경, 메모 API
  - `localStorage` 영속화
  - 요청 지연과 오류 시나리오
- 검증: API 요청·응답, 변경 유지, 오류 처리

### 3. 대시보드

- 브랜치: `feature/dashboard`
- 결과: 운영자가 문의 현황을 빠르게 파악할 수 있는 첫 화면
- 포함:
  - 요약 통계
  - 최근 문의
  - 우선순위 분포
  - 로딩, 오류, 다시 시도
- 검증: 통계 정확성, 상태별 UI, 관련 테스트

### 4. 문의 목록

- 브랜치: `feature/inquiry-list`
- 결과: 운영자가 필요한 문의를 검색하고 분류할 수 있는 목록
- 포함:
  - 문의 테이블과 Badge
  - 검색 Debounce
  - 상태·우선순위·카테고리 필터
  - 정렬과 페이지네이션
  - URL Query Parameter 동기화
  - 로딩·오류·검색 없음·필터 없음
- 검증: 검색, 필터, URL 복원, 요청 경합, 관련 테스트

### 5. 문의 상세와 변경

- 브랜치: `feature/inquiry-detail`
- 결과: 문의 내용을 확인하고 실제 처리 작업을 수행하는 화면
- 포함:
  - 상세 정보
  - 상태·담당자 변경
  - 처리 이력
  - 운영 메모
  - 저장 중·성공·실패 알림
  - 존재하지 않는 문의
- 검증: 변경 반영, 실패 복구, 빈 메모 차단, 관련 테스트

### 6. 반응형 UI와 접근성

- 브랜치: `feature/responsive-ui`
- 결과: 데스크톱·태블릿·모바일에서 사용할 수 있는 UI
- 포함:
  - 모바일 문의 카드
  - 접이식 필터
  - 태블릿 내비게이션
  - 키보드, 포커스, label, `aria-live`
  - `prefers-reduced-motion`
- 검증: 대표 크기와 경계값, 가로 스크롤, 키보드 흐름, 색상 외 텍스트 정보

### 7. 핵심 흐름과 최종 회귀 테스트

- 브랜치: `test/core-flows`
- 결과: 화면을 가로지르는 핵심 흐름과 실패 상황에 대한 회귀 방지
- 포함:
  - 기능 PR에서 부족한 통합 테스트
  - API 실패와 다시 시도
  - 변경 이후 목록·통계 반영
  - 전체 타입·린트·테스트·빌드 확인
- 원칙: 기능 테스트를 이 단계까지 미루지 않고 각 기능 PR에서 먼저 작성합니다.

### 8. 공개 문서와 출시 준비

- 브랜치: `docs/readme`
- 결과: 저장소 방문자가 목적, 구조, 실행 방법, 결과를 이해할 수 있는 README
- 포함:
  - 프로젝트 소개와 실제 구현 기간
  - 화면 이미지 또는 GIF
  - 기술 선택과 사용자 흐름
  - 컴포넌트, API, 상태 관리 구조
  - 반응형, 접근성, 성능, 테스트
  - Vue와 React 차이를 실제 구현에 연결한 내용
  - 검증된 배포 링크와 제한 사항

## 4. 기능 PR 안의 커밋 예시

문의 목록 PR은 다음과 같이 나눌 수 있습니다.

```text
PR: feat: 문의 검색과 필터링이 가능한 목록 구현

├─ feat: 문의 목록 테이블과 상태 배지 구현
├─ feat: 검색과 다중 필터 구현
├─ feat: 필터 상태를 URL 쿼리와 동기화
├─ feat: 목록 로딩 오류 빈 상태 처리
├─ test: 문의 검색과 상태 필터 동작 검증
└─ docs: 문의 목록에서 사용한 Vue 개념 기록
```

실제 구현에서 두 변경이 분리되면 중간 상태가 동작하지 않거나 변경 이유가 같다면 하나의 커밋으로 합칠 수 있습니다. 예시는 목표가 아니라 판단 기준입니다.

## 5. 작업 시작 조건

다음 항목을 확인한 뒤 작업을 시작합니다.

- [ ] 해결할 요구사항과 범위가 `PROJECT_SPEC.md`에 있음
- [ ] 선행 작업이 `main`에 반영되어 있음
- [ ] 브랜치 이름과 PR 목적을 한 문장으로 설명할 수 있음
- [ ] 예상되는 검증 방법을 알고 있음
- [ ] 확정되지 않은 사용자 선택이 결과를 크게 바꾸지 않음

선택이 필요하지만 안전한 기본값으로 진행할 수 있다면 결정과 이유를 `DECISIONS.md`에 기록합니다.

## 6. 작업 완료 조건

다음 조건을 모두 만족해야 작업 단위를 완료로 표시합니다.

### 기능

- [ ] 요구한 사용자 흐름이 실제로 동작함
- [ ] 필요한 로딩·오류·빈 상태를 함께 처리함
- [ ] 이전 기능에 의도하지 않은 회귀가 없음

### 코드

- [ ] TypeScript 오류가 없음
- [ ] ESLint 오류가 없음
- [ ] 컴포넌트와 상태의 책임을 설명할 수 있음
- [ ] 불필요한 추상화와 중복이 없음

### 테스트와 화면

- [ ] 관련 자동화 테스트가 통과함
- [ ] 프로덕션 빌드가 성공함
- [ ] UI 변경이면 관련 화면 크기를 수동 확인함
- [ ] 키보드와 접근성 요구사항을 확인함

### 문서와 Git

- [ ] 학습한 Vue 개념을 실제 파일과 연결해 기록함
- [ ] 새 기술 결정이 있으면 이유를 기록함
- [ ] 커밋이 목적별로 나뉘고 제목과 본문이 있음
- [ ] PR에 변경 목적, 확인 방법, 검증 결과를 작성함
- [ ] 확인하지 않은 결과를 완료로 표시하지 않음

## 7. 작업 보고

각 작업 단위를 마치면 다음 내용을 사용자에게 보고합니다.

- 완성된 사용자 기능
- 주요 구조와 기술 결정
- 실행한 테스트와 수동 검증
- 브랜치와 커밋
- 알려진 제한 사항
- 다음 작업 단위
