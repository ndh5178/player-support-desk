# 기술 결정 기록

구현 중 선택한 구조와 이유를 간단히 기록합니다. 새로운 결정은 기존 항목을 조용히 덮어쓰지 않고 변경 이유와 날짜를 남깁니다.

## 확정된 결정

### D-001. Vue 3 Composition API와 TypeScript

- 상태: 확정
- 날짜: 2026-07-31
- 결정: Vue 3 SFC에서 `<script setup lang="ts">`를 사용합니다.
- 이유: 채용 요구 기술을 학습하면서 React 경험과 비교하기 쉽고, 컴포넌트의 상태와 데이터 계약을 함께 설명할 수 있습니다.

### D-002. 실제 DB 대신 MSW와 localStorage

- 상태: 확정
- 날짜: 2026-07-31
- 결정: REST API는 MSW로 모킹하고, 변경된 데이터는 `localStorage`에 저장합니다.
- 이유: 백엔드 구축보다 프론트엔드 역량에 집중하면서도 조회·수정·오류·지연 등 실제 API 흐름을 구현할 수 있습니다.
- 제한: 브라우저와 저장 공간이 달라지면 데이터가 공유되지 않습니다.

### D-003. API 클라이언트는 fetch 사용

- 상태: 확정
- 날짜: 2026-07-31
- 결정: 별도 HTTP 라이브러리 대신 브라우저 `fetch`와 AbortController를 사용합니다.
- 이유: 현재 API 규모에서 의존성을 늘리지 않고 요청·응답·취소 처리를 직접 설명할 수 있습니다.

### D-004. 설명 가능한 단순 폴더 구조

- 상태: 확정
- 날짜: 2026-07-31
- 결정: `components`, `views`, `stores`, `services`, `mocks`, `types` 중심으로 시작합니다.
- 이유: 처음부터 계층을 과도하게 나누지 않고 Vue의 주요 역할을 폴더에서 바로 파악할 수 있게 합니다.
- 확장 기준: 한 파일의 책임이 둘 이상으로 커지거나 로직이 실제로 반복될 때만 추가 분리합니다.

### D-005. 상태의 위치

- 상태: 확정
- 날짜: 2026-07-31
- 결정:
  - 컴포넌트 입력과 펼침 상태는 로컬 `ref`
  - 파생 값은 `computed`
  - 목록 필터는 URL Query Parameter
  - 여러 화면이 공유하는 문의 서버 상태는 Pinia
- 이유: 모든 값을 전역 Store에 넣지 않고 상태가 필요한 최소 범위에 배치합니다.

### D-006. CSS 중심의 반응형 구현

- 상태: 확정
- 날짜: 2026-07-31
- 결정: CSS 미디어 쿼리, Flex, Grid로 레이아웃을 변경합니다.
- 이유: 화면 배치에 JavaScript `resize` 이벤트가 필요하지 않으며, 브라우저가 제공하는 반응형 기능을 직접 이해하고 구현하기 위함입니다.
- 기준:
  - 모바일: `767px` 이하
  - 태블릿: `768px~1199px`
  - 데스크톱: `1200px` 이상

### D-007. develop 없는 GitHub Flow

- 상태: 확정
- 날짜: 2026-07-31
- 결정: `main`과 짧게 유지되는 작업 브랜치를 사용하고 `develop`은 두지 않습니다.
- 이유: 한 명이 짧은 기간에 개발하고 별도의 통합·스테이징 릴리스가 없어 `develop`의 이점보다 관리 비용이 큽니다.
- 상세 절차: `docs/GIT_WORKFLOW.md`

### D-008. 테스트 범위

- 상태: 확정
- 날짜: 2026-07-31
- 결정: Vitest와 Vue Test Utils로 핵심 사용자 흐름과 오류 처리를 우선 검증합니다.
- 이유: 구현 세부사항보다 사용자가 확인할 수 있는 결과를 테스트하고, 짧은 프로젝트에서 가치가 큰 회귀 방지에 집중합니다.

### D-009. 패키지 관리자는 npm

- 상태: 확정
- 날짜: 2026-07-31
- 결정: 다른 lockfile이 없는 현재 저장소에서는 npm과 `package-lock.json`을 사용합니다.
- 이유: 별도 도구 설치 없이 재현하기 쉽고 Vite 프로젝트의 요구사항을 충족합니다.

### D-010. 사실 기반 포트폴리오 문구

- 상태: 확정
- 날짜: 2026-07-31
- 결정: Vue 숙련도를 과장하지 않고 학습 목적, 구현 범위, 검증 결과를 사실대로 작성합니다.
- 이유: 이 프로젝트의 핵심은 숙련자처럼 보이는 것이 아니라 부족한 기술을 학습해 결과로 만든 실행력을 보여주는 것입니다.

### D-011. TypeScript 6 버전 고정

- 상태: 확정
- 날짜: 2026-07-31
- 결정: TypeScript는 `~6.0.2` 범위로 고정합니다.
- 이유: 설치 시 최신 TypeScript 7과 `vue-tsc` 3.3.8 사이에서 패키지 export 호환 오류가 발생했습니다. `vue-tsc`가 개발에 사용하는 TypeScript 6 계열로 맞춘 뒤 타입 검사가 정상 통과했습니다.
- 후속 확인: `vue-tsc`가 TypeScript 7을 공식 지원하면 업그레이드 가능 여부를 다시 검토합니다.

### D-012. MSW를 애플리케이션 마운트 전에 시작

- 상태: 확정
- 날짜: 2026-07-31
- 결정: 브라우저에서는 MSW Worker 준비가 끝난 뒤 Vue 애플리케이션을 마운트합니다.
- 이유: 첫 화면의 API 요청이 Service Worker 등록보다 먼저 실행되어 실제 네트워크로 빠지는 경합을 방지합니다.
- 예외: 테스트 환경에서는 Node MSW 서버를 사용하고, `VITE_ENABLE_MOCKS=false`이면 브라우저 Worker를 시작하지 않습니다.

### D-013. 개발 의존성 보안 경고 처리

- 상태: 확인 필요
- 날짜: 2026-07-31
- 결정: `npm audit fix --force`를 실행하지 않고 최신 Vue Test Utils를 유지합니다.
- 이유: 현재 경고 6건은 `@vue/test-utils`의 개발 전용 `js-beautify` 의존성에서 발생하며, 강제 수정은 Vue Test Utils를 과거 버전으로 낮춥니다. 프로덕션 런타임은 `npm audit --omit=dev` 기준 취약점 0건입니다.
- 후속 확인: Vue Test Utils 또는 하위 의존성이 갱신되면 전체 `npm audit`를 다시 실행합니다.

### D-014. 상대 시각 기반 Mock 초기 데이터

- 상태: 확정
- 날짜: 2026-07-31
- 결정: 문의의 접수 시각과 SLA 기한은 앱이 초기화되는 시각을 기준으로 계산합니다.
- 이유: 고정된 과거 날짜를 사용하면 시간이 지난 뒤 모든 문의가 SLA 지연으로 보이므로, 포트폴리오를 언제 실행해도 신규·진행·지연 상태를 함께 확인할 수 있게 합니다.
- 재현성: 테스트는 명시한 기준 시각으로 초기화할 수 있습니다.

### D-015. 버전이 있는 localStorage와 메모리 대체 경로

- 상태: 확정
- 날짜: 2026-07-31
- 결정: `player-support-desk:inquiries:v2` 키에 버전과 문의 배열을 저장하고, 손상되거나 호환되지 않는 값은 초기 데이터로 복구합니다.
- 이유: 데이터 구조가 바뀌었을 때 이전 형식을 잘못 읽지 않고 안전하게 초기화하기 위함입니다.
- 예외: 저장 공간 부족이나 접근 제한 환경에서는 같은 세션 동안 메모리 저장소로 동작합니다.

### D-016. 대시보드 조회 상태는 화면에 배치

- 상태: 확정
- 날짜: 2026-07-31
- 결정: 대시보드 데이터, 로딩, 오류는 `DashboardView`의 로컬 `ref`로 관리하고 Pinia Store를 만들지 않습니다.
- 이유: 현재 데이터는 대시보드 한 화면에서만 소비하므로 전역 상태로 올려도 공유 이점이 없습니다. 문의 목록·상세처럼 여러 화면이 변경 결과를 공유하는 시점에 Pinia를 도입합니다.
- 요청 정리: 화면 이탈과 재시도 시 기존 `AbortController`를 취소합니다.

### D-017. Mock 데이터 복제 호환 경로

- 상태: 확정
- 날짜: 2026-07-31
- 결정: `structuredClone`을 우선 사용하고 미지원 환경에서는 JSON 직렬화 복제로 대체합니다.
- 이유: 브라우저 수동 QA에서 `structuredClone` 미지원 환경이 Mock API 500 오류를 만드는 것을 발견했습니다. 문의 데이터는 함수·Date·순환 참조가 없는 JSON 값으로 제한되어 대체 방식이 안전합니다.

### D-018. 문의 목록 조건의 기준은 URL Query

- 상태: 확정
- 날짜: 2026-07-31
- 결정: 검색어, 상태, 우선순위, 카테고리, 정렬, 페이지는 URL Query를 단일 기준으로 두고, Pinia는 조회 결과와 로딩·오류 상태를 관리합니다.
- 이유: 새로고침, 링크 공유, 브라우저 앞·뒤 이동에서도 같은 목록 조건을 복원하면서 화면 입력값과 Store가 서로 다른 필터를 가지는 문제를 막을 수 있습니다.
- 요청 경합: 새 조회 시 이전 요청을 취소하고 현재 요청 식별자를 확인해 오래된 성공·실패 응답을 모두 무시합니다.

### D-019. 상세 원본과 입력 초안의 상태 분리

- 상태: 확정
- 날짜: 2026-07-31
- 결정: API에서 조회·변경한 문의 원본은 Pinia에 두고, 상태·담당자 선택과 메모 입력·검증·성공 알림은 상세 화면과 하위 폼의 로컬 상태로 관리합니다.
- 이유: 저장 실패 시 Store의 확정 값은 유지하면서 사용자가 선택한 값은 폼에 남겨 재시도할 수 있고, 다른 화면에서 사용할 필요가 없는 입력 초안이 전역 상태에 쌓이지 않습니다.
- 변경 동기화: 성공 응답은 상세 원본과 이미 조회한 목록 항목에 함께 반영하며, 메모 생성 응답으로 메모와 처리 이력을 즉시 갱신합니다.

### D-020. SPA 경로 이동의 포커스 계약

- 상태: 확정
- 날짜: 2026-07-31
- 결정: 앱 셸에 본문 바로가기를 제공하고, 실제 경로가 바뀐 뒤 `main`의 첫 `h1`으로 포커스를 옮깁니다. 최초 직접 접속과 URL Query만 바뀌는 목록 조작에서는 포커스를 강제로 이동하지 않습니다.
- 이유: 마우스를 사용하지 않는 사용자에게 새 화면의 시작점을 알리면서도, 첫 화면 로드나 필터 조작 중 현재 포커스를 불필요하게 빼앗지 않기 위함입니다.
- Lazy Loading 대응: 동적 import 화면은 제목이 렌더링될 때까지 짧고 제한된 횟수로 다시 확인하며, 제목이 끝내 없으면 조용히 종료합니다.

### D-021. 접근성 스타일을 디자인 토큰과 자동화 테스트로 보호

- 상태: 확정
- 날짜: 2026-07-31
- 결정: 밝은 배경과 어두운 내비게이션의 포커스 색상을 분리하고, 텍스트·상태 Badge·우선순위 색상의 명도 대비를 자동화 테스트로 검증합니다. 모션은 `prefers-reduced-motion` 설정에서 전역으로 축소합니다.
- 이유: 눈으로 한 번 확인하는 QA만으로는 토큰 변경 시 대비 저하를 놓치기 쉬우며, 사용자의 운영체제 모션 설정은 모든 화면에서 일관되게 존중해야 하기 때문입니다.

### D-022. 통합 테스트는 화면 경계를 넘는 사용자 결과에 집중

- 상태: 확정
- 날짜: 2026-07-31
- 결정: 실제 Router·Pinia·MSW를 연결한 통합 테스트는 상태 변경 이후 목록·대시보드 반영, 앱 재마운트 이후 복원, 실패 재시도의 URL 유지처럼 여러 계층을 지나는 결과만 검증합니다.
- 이유: 개별 컴포넌트 테스트와 같은 세부 렌더링을 반복하면 유지 비용만 늘어납니다. 계층 간 계약이 끊겼을 때만 실패하는 흐름을 선택해야 통합 테스트의 목적이 분명해집니다.
- 브라우저 보완: 실제 새로고침, 포커스, 반응형과 가로 넘침처럼 jsdom이 재현하지 못하는 동작은 수동 브라우저 QA로 확인합니다.

### D-023. 공개 README에는 검증된 결과만 기재

- 상태: 확정
- 날짜: 2026-07-31
- 결정: 실제 구현 기간, 로컬 실행 방법, 테스트 수치와 브라우저 QA 결과는 기재하고, 아직 수행하지 않은 배포의 URL은 임의로 추가하지 않습니다.
- 이유: 포트폴리오 설명은 저장소에서 재현하거나 문서 기록으로 확인할 수 있는 사실과 일치해야 합니다.
- 화면 자료: 동일한 Mock 데이터로 재현한 데스크톱 대시보드·목록과 모바일 상세 화면을 저장소의 `docs/images`에 포함합니다.

### D-024. 배틀그라운드 지원 도구는 비공식 UI 콘셉트로 표현

- 상태: 확정
- 날짜: 2026-08-01
- 결정: 포트폴리오의 제품 맥락을 배틀그라운드 플레이어 지원 운영 도구로 구체화하되, 공식 로고와 게임 이미지는 사용하지 않고 전술 지도에서 가져온 색상·격자·상태 표식만 자체 CSS로 구현합니다.
- 이유: 어떤 게임과 운영 상황을 가정했는지 UI와 데이터에서 즉시 전달하면서도 실제 공식 서비스로 오인될 가능성과 불필요한 저작물 의존을 줄이기 위함입니다.
- 공개 표기: 앱 셸과 README에 비공식 학습·포트폴리오 콘셉트임을 명시합니다.
